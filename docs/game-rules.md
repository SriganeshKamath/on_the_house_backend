# On the House — Game Rules

## 1. Purpose

**On the House** is a real-time multiplayer Housie game designed to be played with friends.

A player can create a lobby, receive a unique game code, and share that code with friends. Other players use the code to join the lobby. Once all players have joined, the host configures the game settings and starts the game.

The game is played in real time. The server is the authoritative source of truth for all game state, number calling, ticket state, prize validation, points, and game completion.

---

## 2. Core Game Concept

The game follows the standard 90-ball Housie/Tambola concept:

* The game uses numbers from `1` to `90`.
* Each player receives a Housie ticket.
* The server calls numbers one at a time.
* Players mark numbers on their own tickets when those numbers are called.
* Players can claim prizes when their ticket satisfies the requirements of a prize.
* The server validates every prize claim.
* Valid prize claims are recorded and broadcast to all players in real time.
* Players who become spectators can continue watching the game but can no longer participate in gameplay or claim prizes.

---

## 3. Game Participants

A game consists of:

* One **Host**.
* One or more **Players**. 
* Players may become **Spectators** during the game.

### Host

The host is the player who creates the lobby.

The host is responsible for:

* Creating the lobby.
* Sharing the game code with friends.
* Waiting for players to join.
* Configuring game settings before the game starts.
* Starting the game.
* Can also play game with other players.

Once the game starts, settings that affect gameplay are locked unless an explicit game rule allows them to be changed.

### Player

A player:

* Joins a lobby using the game code.
* Receives a ticket when the game starts.
* Participates in number marking.
* Can claim eligible prizes.
* Accumulates points from successfully claimed prizes.

### Spectator

A player becomes a spectator when they win Full House.

A spectator:

* Remains connected to the game.
* Can continue viewing the game.
* Can receive real-time game updates.
* Cannot mark numbers.
* Cannot claim additional prizes.
* Cannot receive additional prize points.

---

## 4. Server Authority

The backend server is the authoritative source of truth.

The client application must never be trusted to determine whether a game action is valid.

The server is responsible for determining:

* Which numbers have been called.
* The order in which numbers were called.
* Whether a number can be marked.
* Whether a player's ticket contains a number.
* Whether a prize has been completed.
* Whether a player is eligible for a prize.
* Whether a prize is still available.
* Whether a player has already claimed a restricted prize.
* The points awarded to a player.
* Whether a player becomes a spectator.
* Whether the game has finished.

The client is responsible only for presenting the current game state and sending player actions to the server.

---

## 5. Number Calling

The game uses the numbers:

```text
1, 2, 3, ... 90
```

Numbers are called by the server.

Rules:

* A number can only be called once during a game.
* The server randomly selects the next uncalled number.
* The server records every called number.
* The server records the order in which numbers were called.
* The server broadcasts each newly called number to all connected players.
* Clients must not generate or select numbers themselves.

The interval between called numbers is configured by the host before the game starts.

Allowed interval:

```text
Minimum: 5 seconds
Maximum: 30 seconds
```

The exact number-calling behavior and timer rules are defined in `game-lifecycle.md` and the relevant game engine documentation.

---

## 6. Player Tickets

Every participating player receives a Housie ticket when the game starts.

Tickets are generated by the server.

The client must not generate or modify a player's authoritative ticket.

The server maintains the authoritative representation of each player's ticket and its marking state.

A player can only mark a number when:

1. The number exists on their ticket.
2. The number has already been called by the server.
3. The player is currently eligible to participate.

Detailed ticket structure and generation rules are defined in `ticket-rules.md`.

---

## 7. Prize System

The game contains the following prize categories:

| Prize               | Points |
| ------------------- | -----: |
| Star                |     15 |
| First Row           |     10 |
| Second Row          |     10 |
| Third Row           |     10 |
| Full House          |     30 |
| House to Follow #1  |     20 |
| House to Follow #2  |     15 |
| House to Follow #3+ |     10 |

The host determines the number of **House to Follow** prizes before the game begins.

The number of House to Follow prizes must be at least `1`.

The maximum number of House to Follow prizes is:

```text
number of players - 1
```

The detailed requirements, eligibility rules, restrictions, and evaluation logic for each prize are defined in `prize-rules.md`.

---

## 8. Prize Claiming

Players do not automatically receive a prize merely because their ticket satisfies its requirements.

A player must explicitly claim a prize.

The server validates the claim.

General claim flow:

```text
Player requests prize claim
        ↓
Server validates player
        ↓
Server validates game state
        ↓
Server validates prize availability
        ↓
Server validates player eligibility
        ↓
Server evaluates ticket
        ↓
Server accepts or rejects claim
        ↓
If valid:
    Record prize claim
    Award points
    Update player state if required
    Broadcast result
```

The client must never directly award points or mark a prize as won.

---

## 9. Row Prize Restriction

There are three row prizes:

* First Row
* Second Row
* Third Row

A player may claim **at most one row prize during a game**.

For example:

```text
Player A → First Row → Allowed

Player A → Second Row → Not Allowed

Player A → Third Row → Not Allowed
```

Winning one row prize does not prevent the player from subsequently claiming other eligible prize categories such as Full House or House to Follow, subject to the specific rules of those prizes.

---

## 10. Full House

Full House awards:

```text
30 points
```

A player completes Full House when all numbers on their ticket satisfy the Full House requirement.

When a player successfully wins Full House:

```text
Player Status
ACTIVE
   ↓
SPECTATOR
```

The player has completed their participation in prize claiming for the game.

They remain able to observe the game until it ends.

A Full House winner cannot claim subsequent House to Follow prizes.

---

## 11. House to Follow

House to Follow prizes are configured by the host before the game starts.

The points are assigned according to prize sequence:

```text
House to Follow #1 → 20 points
House to Follow #2 → 15 points
House to Follow #3 → 10 points
House to Follow #4 → 10 points
House to Follow #5 → 10 points
...
```

Therefore, after the second House to Follow prize, every subsequent House to Follow prize is worth `10` points.

A player who wins a House to Follow prize is not eligible to win a subsequent House to Follow prize in the same game.

A player who has won Full House is also not eligible for House to Follow prizes.

Detailed House to Follow rules are defined in `prize-rules.md`.

---

## 12. Points

Points are awarded only after the server successfully validates and records a prize claim.

The client must never determine the number of points awarded.

The server calculates the points from the prize definition.

A player's score is the sum of their successfully awarded prize points.

Example:

```text
Star          = 15
First Row     = 10
Full House    = 30
-------------------
Total         = 55
```

---

## 13. Game State Integrity

The following game information must be authoritative on the server:

```text
Game status
Game settings
Players
Player statuses
Tickets
Called numbers
Number-call order
Marked ticket numbers
Prize availability
Prize claims
Prize winners
Player scores
Game completion state
```

Clients may maintain temporary UI state, but such state must not override or replace the authoritative server state.

---

## 14. Real-Time Requirement

The game is a real-time multiplayer application.

Important game events must be communicated to connected players in real time.

Examples include:

```text
Player joined
Player left
Game settings changed
Game started
Number called
Number marked
Prize claimed
Prize won
Player became spectator
Game finished
```

Socket.IO is used for real-time communication.

REST APIs are used for resource-oriented operations such as authentication, lobby creation, lobby retrieval, and retrieving persistent game information.

---

## 15. Concurrent Actions

Multiple players may perform actions at nearly the same time.

The server must handle concurrent prize claims safely.

For a prize where only one winner is allowed:

```text
Player A claims
Player B claims almost simultaneously
```

The backend must ensure that the database and game state cannot record two winners when only one winner is permitted.

Prize claiming must therefore be treated as an atomic server-side operation and must use appropriate database transaction/constraint mechanisms.

The exact simultaneous-claim resolution rule is defined in `prize-rules.md`.

---

## 16. Client Trust Model

The client may request an action but cannot authorize the action.

Examples:

```text
Client:
"I want to mark 37."

Server:
"Was 37 called?"
"Is 37 on this player's ticket?"
"Is this player active?"
```

Similarly:

```text
Client:
"I want to claim Full House."

Server:
"Is the player eligible?"
"Is Full House still available?"
"Does the ticket satisfy Full House?"
"Has the player already won a conflicting prize?"
```

The server makes the final decision.

---

## 17. Core Game Invariants

The backend must always preserve these invariants:

1. A game cannot call the same number twice.
2. A called number must belong to the range `1–90`.
3. A player cannot modify their authoritative ticket.
4. A player cannot mark an uncalled number.
5. A player cannot mark a number that does not exist on their ticket.
6. A spectator cannot participate in gameplay.
7. A spectator cannot claim prizes.
8. A player cannot claim more than one row prize.
9. A Full House winner becomes a spectator.
10. A Full House winner cannot claim House to Follow.
11. A House to Follow winner cannot win another House to Follow prize.
12. Prize points can only be awarded by the server.
13. A prize cannot be awarded more times than configured.
14. Game settings that are locked at game start cannot be modified through the client.
15. Game state transitions must be controlled by the server.
16. Concurrent requests must not violate prize or game-state rules.

## 19. Backend Design Principle

The backend should be designed around the following principle:

```text
Client requests an action
        ↓
Server validates the action
        ↓
Domain/Game logic evaluates the action
        ↓
Database transaction persists the result
        ↓
Server broadcasts the authoritative result
        ↓
Clients update their UI
```

The backend must never rely on the client to enforce game rules.
