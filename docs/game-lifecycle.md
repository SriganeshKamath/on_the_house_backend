# On the House — Game Lifecycle

## 1. Purpose

This document defines the complete lifecycle of an **On the House** multiplayer game.

It specifies:

* Lobby states.
* Game states.
* State transitions.
* Actions allowed in each state.
* Host responsibilities.
* Player responsibilities.
* Game-start conditions.
* Game-end conditions.
* Rules for joining, leaving, reconnecting, and starting.
* Server authority over state transitions.

The backend must enforce these lifecycle rules on the server.

---

# 2. High-Level Lifecycle

The overall lifecycle is:

```text
LOBBY CREATED
      ↓
WAITING FOR PLAYERS
      ↓
SETTINGS CONFIGURED
      ↓
STARTING
      ↓
IN PROGRESS
      ↓
FINISHED
```

A more detailed representation:

```text
                     ┌─────────────────┐
                     │ LOBBY CREATED   │
                     └────────┬────────┘
                              ↓
                     ┌─────────────────┐
                     │ WAITING         │
                     │ FOR PLAYERS     │
                     └────────┬────────┘
                              ↓
                     Host configures
                         settings
                              ↓
                     ┌─────────────────┐
                     │ SETTINGS READY  │
                     └────────┬────────┘
                              ↓
                       Host starts game
                              ↓
                     ┌─────────────────┐
                     │ STARTING        │
                     └────────┬────────┘
                              ↓
                     Generate tickets
                              ↓
                     Initialize game
                              ↓
                     ┌─────────────────┐
                     │ IN_PROGRESS     │
                     └────────┬────────┘
                              ↓
                    All prizes completed
                              ↓
                     ┌─────────────────┐
                     │ FINISHED        │
                     └─────────────────┘
```

---

# 3. Lobby and Game Are Separate Concepts

The system must distinguish between a **Lobby** and a **Game**.

### Lobby

A lobby is the pre-game environment where players gather.

It is responsible for:

* Game code.
* Host.
* Players joining/leaving.
* Player count.
* Game settings before the game starts.
* Starting the game.

### Game

A game is the actual Housie session created from the lobby.

It is responsible for:

* Game settings.
* Player tickets.
* Called numbers.
* Number-call sequence.
* Marked numbers.
* Prize claims.
* Player scores.
* Player statuses.
* Game completion.

Conceptually:

```text
Lobby
  │
  │ Host starts
  ↓
Game
```

Once the game starts, the lobby's pre-game configuration becomes locked.

---

# 4. Lobby States

The lobby should have explicit server-side states.

Recommended states:

```text
WAITING
STARTING
IN_PROGRESS
FINISHED
CANCELLED
```

### WAITING

The lobby has been created and players can join.

Allowed:

* Host views lobby.
* Host shares game code.
* Players join.
* Players leave.
* Host removes players.
* Host configures game settings.
* Host starts the game when valid.

### STARTING

The host has initiated the game start process.

The server is:

* Locking the lobby.
* Creating the game.
* Creating game players.
* Generating tickets.
* Initializing game settings.
* Preparing the number caller.

No new players may join during this state.

### IN_PROGRESS

The game is actively being played.

Players can:

* Receive called numbers.
* Mark valid numbers.
* Claim eligible prizes.
* Leave/reconnect according to the reconnection rules.

Players cannot:

* Change game settings.
* Join as new players.
* Receive a new ticket.
* Change the number-calling speed.
* Change the House to Follow count.

### FINISHED

The game has ended.

No gameplay actions are allowed.

Players can:

* View final scores.
* View prize winners.
* View game results.
* Remain connected to view the final game state.

### CANCELLED

The lobby/game has been cancelled before completion.

No gameplay actions are allowed.

---

# 5. Lobby Creation

A user creates a lobby through the backend.

Flow:

```text
Authenticated User
       ↓
POST /lobbies
       ↓
Server creates Lobby
       ↓
Generate unique game code
       ↓
Set host
       ↓
Set status = WAITING
       ↓
Return lobby information
```

The game code must be:

* Generated by the server.
* Unique among active lobbies.
* Safe to share with other players.
* Case-insensitive from the user's perspective if the implementation chooses to support that behavior.

The client must not generate the authoritative lobby code.

---

# 6. Joining a Lobby

A player joins using the game code.

Flow:

```text
Player enters code
       ↓
Server receives join request
       ↓
Find lobby
       ↓
Validate lobby status
       ↓
Validate player eligibility
       ↓
Validate lobby capacity
       ↓
Create LobbyPlayer
       ↓
Join Socket.IO room
       ↓
Broadcast player joined
```

A player cannot join a lobby when:

```text
status != WAITING
```

A player cannot join if the lobby is full.

A player cannot be added more than once to the same lobby.

---

# 7. Lobby Player List

The server maintains the authoritative list of lobby participants.

When a player joins:

```text
player:joined
```

is broadcast to the lobby.

When a player leaves:

```text
player:left
```

is broadcast to the lobby.

The client should derive the displayed player list from server state rather than assuming that a local Socket.IO connection represents a valid game participant.

---

# 8. Host Responsibilities

The host can perform host-only actions while the lobby is in `WAITING`.

Host-only actions include:

```text
Configure game settings
Start game
Cancel lobby
```

The backend must verify that the requesting user is actually the host.

A client must not be able to become host by simply sending a host-related request.

---

# 9. Game Settings

The host configures the game before starting.

Current settings include:

### Number Calling Interval

Allowed range:

```text
Minimum = 5 seconds
Maximum = 30 seconds
```

### House to Follow Count

Allowed range:

```text
Minimum = 1
Maximum = number of players - 1
```

Example:

```text
Players = 6

Minimum H2F = 1
Maximum H2F = 5
```

The server must validate these constraints.

The client must not be trusted to provide valid values.

---

# 10. Settings Lock

Game settings are configurable only before the game starts.

Once the game transitions to `STARTING`:

```text
Settings become immutable.
```

This includes:

* Number calling interval.
* House to Follow count.
* Other gameplay settings introduced in future versions.

Any attempt to modify locked settings must be rejected by the server.

---

# 11. Starting the Game

Only the host can start the game.

The start request is valid only when:

```text
Lobby status = WAITING
```

The server performs the following operations:

```text
Validate host
      ↓
Validate lobby
      ↓
Validate player count
      ↓
Validate game settings
      ↓
Lock lobby
      ↓
Transition to STARTING
      ↓
Create Game
      ↓
Create GamePlayers
      ↓
Generate tickets
      ↓
Initialize game state
      ↓
Transition to IN_PROGRESS
      ↓
Broadcast game started
```

The entire initialization process must be controlled by the server.

---

# 12. Ticket Generation During Start

Tickets are generated after the lobby is locked and before gameplay begins.

For each participating player:

```text
LobbyPlayer
      ↓
GamePlayer
      ↓
Generate Ticket
      ↓
Persist Ticket
```

The server must ensure that every active player receives exactly one authoritative ticket for the game.

The ticket must exist before the game begins calling numbers.

Detailed ticket rules are defined in `ticket-rules.md`.

---

# 13. Transition to IN_PROGRESS

The game enters `IN_PROGRESS` only after all required initialization has succeeded.

Required initialization includes:

* Game created.
* Game settings stored.
* Game players created.
* Tickets generated.
* Initial game state created.
* Number caller ready.

Only after successful initialization should the server broadcast:

```text
game:started
```

If initialization fails, the game must not enter `IN_PROGRESS`.

The server should handle the failure safely and prevent partially initialized games from becoming playable.

---

# 14. Game in Progress

During `IN_PROGRESS`, the server controls gameplay.

The main cycle is:

```text
Call number
      ↓
Persist called number
      ↓
Broadcast number
      ↓
Players mark numbers
      ↓
Players claim prizes
      ↓
Evaluate claims
      ↓
Award valid prizes
      ↓
Update player state
      ↓
Continue calling
```

The game engine is responsible for coordinating this process.

---

# 15. Number Calling Lifecycle

The number caller operates only while:

```text
Game status = IN_PROGRESS
```

Each number-call cycle:

```text
Select uncalled number
      ↓
Persist CalledNumber
      ↓
Broadcast number-called
      ↓
Wait configured interval
      ↓
Repeat
```

The server must never call a number that has already been called.

If the game finishes, the number caller must stop.

---

# 16. Player Actions During Gameplay

An `ACTIVE` player may:

```text
Mark a valid called number
Claim an eligible prize
Leave the game
Reconnect after disconnection
```

A `SPECTATOR` may:

```text
Observe the game
Receive game events
View called numbers
View prize results
View final results
```

A `SPECTATOR` may not:

```text
Mark numbers
Claim prizes
Receive new gameplay privileges
```

A player whose status is `LEFT` cannot perform gameplay actions unless the reconnection rules explicitly restore them to the game.

---

# 17. Number Marking Lifecycle

When a player attempts to mark a number:

```text
Client
  ↓
mark-number
  ↓
Server
  ↓
Validate game state
  ↓
Validate player status
  ↓
Validate number range
  ↓
Validate number was called
  ↓
Validate number exists on player's ticket
  ↓
Mark number
  ↓
Persist state
  ↓
Send result to player
```

The client cannot mark numbers directly in the authoritative database.

---

# 18. Prize Claim Lifecycle

When a player claims a prize:

```text
Client
  ↓
claim-prize
  ↓
Server
  ↓
Validate game state
  ↓
Validate player status
  ↓
Validate prize
  ↓
Validate prize availability
  ↓
Validate player eligibility
  ↓
Evaluate ticket
  ↓
If valid:
    Create PrizeClaim
    Award points
    Update player state
    Broadcast result
```

Prize evaluation rules are defined in `prize-rules.md`.

---

# 19. Full House Transition

When a player successfully wins Full House:

```text
GamePlayer.status

ACTIVE
   ↓
SPECTATOR
```

The transition must be performed by the server as part of the successful Full House claim.

The client must not independently change the player's status.

After becoming a spectator:

```text
mark-number → rejected
claim-prize → rejected
```

The player continues receiving game updates.

---

# 20. Game Completion

The game normally finishes when all configured prizes have been successfully claimed.

Example:

```text
Star                    ✓
First Row               ✓
Second Row              ✓
Third Row               ✓
Full House              ✓
House to Follow #1      ✓
House to Follow #2      ✓
House to Follow #3      ✓
```

Once all required prizes have been awarded:

```text
IN_PROGRESS
     ↓
FINISHED
```

The server must:

1. Stop number calling.
2. Prevent further gameplay actions.
3. Persist the final game state.
4. Calculate/finalize player scores.
5. Broadcast `game:finished`.
6. Make final results available.

The exact game-end conditions may be extended in future versions, but every completion path must result in a consistent `FINISHED` state.

---

# 21. Automatic End Due to All Numbers Being Called

If all numbers from `1` to `90` have been called before all configured prizes have been claimed, the server must follow the explicitly defined end-of-number policy.

The initial implementation should not silently assume that calling number `90` automatically ends the game.

The final policy must be defined before implementing the game engine.

---

# 22. Player Leaving Before Game Start

A player may leave while the lobby is in `WAITING`.

Flow:

```text
Player leaves
      ↓
Remove/mark LobbyPlayer as left
      ↓
Update player count
      ↓
Broadcast player:left
```

If the host leaves before the game starts, host transfer behavior must be explicitly defined.

Recommended initial rule:

```text
Host leaves
    ↓
Lobby is cancelled
```

Host transfer can be introduced later if required.

---

# 23. Player Leaving During Game

A player leaving during `IN_PROGRESS` does not automatically end the game.

Their GamePlayer status should be updated to:

```text
LEFT
```

Their historical:

* Ticket.
* Called-number history.
* Prize claims.
* Score.

must remain intact.

Whether the player can reconnect and return to the game is governed by the reconnection rules.

---

# 24. Reconnection

A temporary Socket.IO disconnection must not automatically destroy a player's game data.

The database remains the source of truth.

When a player reconnects:

```text
Socket reconnects
      ↓
Authenticate player
      ↓
Identify active GamePlayer
      ↓
Join game room
      ↓
Retrieve current game state
      ↓
Send synchronized state
```

The player must receive enough authoritative state to reconstruct the current game view.

This may include:

* Game status.
* Player status.
* Player ticket.
* Marked numbers.
* Called numbers.
* Current prize claims.
* Player score.
* Remaining prizes.
* Current game settings.

---

# 25. Invalid State Transitions

The server must reject invalid transitions.

Examples:

```text
FINISHED → IN_PROGRESS       ✗
FINISHED → WAITING           ✗
IN_PROGRESS → WAITING        ✗
WAITING → FINISHED           ✗
SPECTATOR → ACTIVE           ✗
```

unless a future explicitly defined rule allows the transition.

State transitions must be centralized rather than duplicated throughout controllers and Socket.IO handlers.

---

# 26. State Transition Authority

Only the server can change authoritative lifecycle states.

Clients can request actions:

```text
"Start game"
"Leave game"
"Mark number"
"Claim prize"
```

The server decides whether the action causes a state transition.

Example:

```text
Client:
START GAME

        ↓

Server:
Is requester host?
Is lobby WAITING?
Are settings valid?
Are there enough players?

        ↓

YES

        ↓

WAITING → STARTING → IN_PROGRESS
```

---

# 27. Recommended State Machine

The backend should conceptually enforce the following state machine:

```text
                     ┌──────────────┐
                     │   WAITING    │
                     └──────┬───────┘
                            │
                       Host starts
                            │
                            ▼
                     ┌──────────────┐
                     │   STARTING   │
                     └──────┬───────┘
                            │
                  Initialization succeeds
                            │
                            ▼
                     ┌──────────────┐
                     │ IN_PROGRESS  │
                     └──────┬───────┘
                            │
                  All required prizes
                       are completed
                            │
                            ▼
                     ┌──────────────┐
                     │   FINISHED   │
                     └──────────────┘


WAITING
   │
   │ Host cancels / host leaves
   ▼
CANCELLED
```

---

# 28. Important Lifecycle Invariants

The following must always be true:

1. Only a host can start a game.
2. A lobby must be in `WAITING` before it can start.
3. Game settings cannot be changed after the game starts.
4. New players cannot join after the lobby is locked.
5. Every active GamePlayer receives exactly one ticket.
6. Number calling occurs only during `IN_PROGRESS`.
7. Called numbers are never repeated.
8. Gameplay actions are accepted only during `IN_PROGRESS`.
9. Spectators cannot mark numbers.
10. Spectators cannot claim prizes.
11. Full House changes the winner's status to `SPECTATOR`.
12. A finished game cannot accept gameplay actions.
13. A player's historical game data must remain available after they leave.
14. Temporary Socket.IO disconnection must not destroy persistent game state.
15. All lifecycle transitions are controlled by the server.
16. A failed game initialization must not produce a playable partially initialized game.
