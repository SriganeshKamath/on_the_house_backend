# On the House — Ticket Rules

## 1. Purpose

This document defines the authoritative rules for player tickets in **On the House**.

It specifies:

* Ticket structure.
* Number ranges.
* Row and column constraints.
* Number placement.
* Blank cells.
* Ticket generation.
* Ticket uniqueness requirements.
* Number marking.
* Server authority.
* Validation requirements.
* Rules required by the game evaluation system.

The ticket generator and ticket evaluators must follow this document.

---

# 2. Ticket Type

On the House uses the standard **90-ball Housie/Tambola ticket format**.

Each ticket contains:

```text
3 rows
9 columns
15 numbers
```

Therefore:

```text
3 × 9 = 27 cells
15 occupied cells
12 blank cells
```

Each row contains exactly:

```text
5 numbers
4 blank cells
```

The ticket therefore contains:

```text
5 + 5 + 5 = 15 numbers
```

---

# 3. Ticket Layout

A ticket is represented as a `3 × 9` grid.

Example:

```text
┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
│  4 │    │ 23 │    │ 41 │    │    │ 72 │ 89 │
├────┼────┼────┼────┼────┼────┼────┼────┼────┤
│    │ 17 │    │ 36 │    │ 52 │ 63 │    │ 84 │
├────┼────┼────┼────┼────┼────┼────┼────┼────┤
│  8 │    │ 29 │ 38 │    │    │ 67 │ 75 │    │
└────┴────┴────┴────┴────┴────┴────┴────┴────┘
```

Each cell has one of two states:

```text
OCCUPIED
BLANK
```

An occupied cell contains exactly one number.

A blank cell contains no number.

---

# 4. Number Range by Column

Numbers must follow standard 90-ball Housie column ranges.

The nine columns correspond to:

| Column | Number Range |
| ------ | ------------ |
| 1      | 1–9          |
| 2      | 10–19        |
| 3      | 20–29        |
| 4      | 30–39        |
| 5      | 40–49        |
| 6      | 50–59        |
| 7      | 60–69        |
| 8      | 70–79        |
| 9      | 80–90        |

Therefore:

```text
Column 1 → 1–9
Column 2 → 10–19
Column 3 → 20–29
Column 4 → 30–39
Column 5 → 40–49
Column 6 → 50–59
Column 7 → 60–69
Column 8 → 70–79
Column 9 → 80–90
```

The number `90` belongs only to column 9.

A number outside the range of its column is invalid.

---

# 5. Number Uniqueness

A number may appear only once on a single ticket.

For example:

```text
37
37
```

on the same ticket is invalid.

All 15 numbers on a ticket must be unique.

The same number may appear on different players' tickets.

Example:

```text
Player A → 37
Player B → 37
```

is valid.

Ticket uniqueness is therefore enforced **within a ticket**, not globally across the game.

---

# 6. Row Constraints

Every row must contain exactly five numbers.

Example:

```text
Row 1 → 5 numbers
Row 2 → 5 numbers
Row 3 → 5 numbers
```

Therefore:

```text
Total = 15 numbers
```

No row may contain:

```text
0 numbers
1 number
2 numbers
3 numbers
4 numbers
6+ numbers
```

A generated ticket violating this rule is invalid.

---

# 7. Column Constraints

Every column must contain at least one number unless the ticket-generation algorithm explicitly follows a valid standard Housie generation strategy that permits an empty column.

The implementation must ensure that the final ticket is a valid standard 90-ball Housie ticket.

The backend must not assume that every column necessarily contains the same number of values.

A column may contain:

```text
1 number
2 numbers
3 numbers
```

subject to the overall ticket constraints.

---

# 8. Ordering Within Columns

Numbers within a column must be ordered from top to bottom.

For example:

```text
Column 5:

41
45
48
```

is valid.

But:

```text
48
41
45
```

is invalid.

The ticket generator must ensure that the numeric values increase from top to bottom within each column where multiple cells in the column are occupied.

---

# 9. Blank Cells

Blank cells contain no number.

They must not be interpreted as:

```text
0
null number
negative number
random number
```

The backend representation should clearly distinguish an empty cell from an occupied cell.

For example, conceptually:

```text
{
    row: 0,
    column: 3,
    number: null
}
```

represents a blank cell.

An occupied cell could be:

```text
{
    row: 0,
    column: 3,
    number: 37
}
```

The exact database representation is defined by `domain-model.md` and the Prisma schema.

---

# 10. Ticket Generation

Tickets must be generated by the backend.

The client must never generate the authoritative ticket.

The ticket generation process must:

1. Create a valid `3 × 9` layout.
2. Place exactly 15 numbers.
3. Place exactly 5 numbers in each row.
4. Respect column number ranges.
5. Ensure numbers are unique within the ticket.
6. Order numbers correctly within each column.
7. Produce a valid standard 90-ball Housie ticket.
8. Persist the generated ticket before gameplay begins.

---

# 11. Ticket Generation Timing

Tickets are generated when the game is initialized.

The expected flow is:

```text
Host starts game
      ↓
Validate lobby
      ↓
Create game
      ↓
Create game players
      ↓
Generate ticket for each active player
      ↓
Persist tickets
      ↓
Game becomes IN_PROGRESS
```

A player must not receive a new random ticket every time they reconnect.

The ticket assigned to a player for a game remains their authoritative ticket for that game.

---

# 12. Ticket Persistence

The server must persist the ticket.

A ticket must survive:

* Socket disconnection.
* Player reconnection.
* Application restart.
* Game result retrieval.
* Game completion.

The database is the authoritative source for the ticket.

In-memory game state may be used for performance, but it must not be the only source of ticket information.

---

# 13. Ticket Marking

A ticket number can have a marked/unmarked state.

Initially:

```text
All numbers = UNMARKED
```

When a player marks a valid number:

```text
UNMARKED
    ↓
MARKED
```

A number can only become marked when the server verifies that the corresponding number has already been called.

---

# 14. Number Marking Validation

When a player requests to mark a number, the server must validate:

### 1. Game state

The game must be:

```text
IN_PROGRESS
```

### 2. Player state

The player must be:

```text
ACTIVE
```

### 3. Number range

The number must be between:

```text
1 and 90
```

### 4. Called status

The number must already have been called by the server.

### 5. Ticket ownership

The number must exist on the player's ticket.

### 6. Marking state

The number must not already be marked.

If any validation fails, the server rejects the marking request.

---

# 15. Marking Is Server-Authoritative

The client may visually mark a number immediately for UI responsiveness, but this is only temporary UI state.

The authoritative state is determined by the server.

Example:

```text
Client:
Player taps 37
    ↓
Client requests mark
    ↓
Server validates
    ↓
Server accepts
    ↓
Database updated
    ↓
Server confirms mark
```

The client must reconcile its UI with the server response.

---

# 16. Players Cannot Modify Ticket Structure

A player must never be able to:

* Change a number.
* Move a number.
* Add a number.
* Remove a number.
* Change a blank cell into a number.
* Change the position of a number.
* Generate a replacement ticket.

The only ticket state a player may change during normal gameplay is the **marked/unmarked state**, and even that change must be validated by the server.

---

# 17. Ticket Ownership

Each active player must have exactly one ticket for a particular game.

Conceptually:

```text
Game
 ├── Player A → Ticket A
 ├── Player B → Ticket B
 ├── Player C → Ticket C
 └── Player D → Ticket D
```

A ticket belongs to exactly one GamePlayer within a game.

A player cannot use another player's ticket to claim a prize.

---

# 18. Ticket Evaluation

The ticket evaluation system must operate on authoritative server state.

Evaluation may consider:

```text
Ticket layout
+
Ticket numbers
+
Called numbers
+
Marked numbers
+
Game state
+
Player state
```

The evaluation system must not trust a client-provided representation of the ticket.

For example, a client must not send:

```text
{
    "completedRows": [1, 2]
}
```

and expect the server to trust it.

Instead, the server calculates row completion from the authoritative ticket and called/marked state.

---

# 19. Prize Evaluation Dependencies

The ticket structure must support evaluation of:

```text
Star
First Row
Second Row
Third Row
Full House
House to Follow
```

The evaluator must be able to determine:

* Whether a specific ticket position is occupied.
* What number exists at a specific position.
* Whether that number has been called.
* Whether that number is marked.
* Whether all numbers in a row satisfy the required condition.
* Whether all 15 ticket numbers satisfy Full House.

Detailed prize evaluation rules are defined in `prize-rules.md`.

---

# 20. Star Position Evaluation

The Star prize depends on specific ticket positions.

The ticket evaluator must therefore preserve the exact `row` and `column` position of every occupied cell.

The evaluator must not attempt to determine Star positions merely from the numeric values.

For example:

```text
row = 0, column = 0
row = 0, column = 8
row = 1, column = 4
row = 2, column = 0
row = 2, column = 8
```

represent the five geometric Star positions if those positions are part of the finalized Star rule.

The exact Star interpretation is defined in `prize-rules.md`.

---

# 21. Row Evaluation

A row is considered complete only when every occupied number in that row satisfies the requirements of the game.

For a standard ticket:

```text
Row 1 → 5 numbers
Row 2 → 5 numbers
Row 3 → 5 numbers
```

Therefore:

```text
First Row completed
    ⇔
all 5 First Row numbers are validly completed

Second Row completed
    ⇔
all 5 Second Row numbers are validly completed

Third Row completed
    ⇔
all 5 Third Row numbers are validly completed
```

The evaluator must derive these values from the ticket rather than trusting the client.

---

# 22. Full House Evaluation

A Full House requires all 15 numbers on the player's ticket to satisfy the Full House condition.

Conceptually:

```text
15 ticket numbers
       ↓
all satisfied
       ↓
Full House = TRUE
```

If even one required ticket number has not been called/marked according to the finalized game rule:

```text
Full House = FALSE
```

The exact distinction between "called" and "marked" must be consistent throughout the game implementation.

The final Full House rule is defined in `prize-rules.md`.

---

# 23. Ticket Validation

The backend should provide a reusable ticket validation mechanism.

Conceptually:

```text
validateTicket(ticket)
```

It should verify:

```text
✓ 3 rows
✓ 9 columns
✓ 15 occupied cells
✓ 5 numbers per row
✓ Valid number ranges
✓ No duplicate numbers
✓ Correct column ordering
✓ Valid blank/occupied structure
```

Invalid tickets must never be persisted as playable tickets.

---

# 24. Ticket Generator and Ticket Evaluator Separation

Ticket generation and ticket evaluation are separate responsibilities.

### Ticket Generator

Responsible for:

```text
Creating a valid ticket
```

### Ticket Evaluator

Responsible for:

```text
Determining whether an existing ticket satisfies game conditions
```

They should not be combined into one module.

Recommended structure:

```text
evaluation/
└── ticket/
    ├── ticket-validator.js
    ├── row-evaluator.js
    └── position-evaluator.js

game/
└── ticket/
    └── ticket-generator.js
```

The exact folder structure may evolve during implementation.

---

# 25. Randomness

Ticket generation must use server-side randomness.

The client must not provide:

```text
ticket numbers
number positions
random seed
```

as authoritative input.

If reproducible randomness is ever required for debugging or auditing, the implementation may introduce a server-side seed mechanism later.

The initial implementation does not require client-controlled seeds.

---

# 26. Ticket Uniqueness Across Players

Two players are allowed to receive tickets containing the same numbers.

The initial game implementation does not require every player's ticket to be mathematically unique from every other player's ticket.

The important requirement is:

```text
No duplicate number within one ticket.
```

If global ticket uniqueness becomes a product requirement later, it can be added separately.

---

# 27. Reconnection and Tickets

A player's ticket must remain unchanged after reconnection.

Example:

```text
Game starts
    ↓
Player A receives Ticket A
    ↓
Player A disconnects
    ↓
Player A reconnects
    ↓
Server retrieves Ticket A
    ↓
Player A continues with Ticket A
```

A reconnecting player must never receive a newly generated ticket.

---

# 28. Ticket Security

The server should expose only the ticket belonging to the authenticated player through normal player-facing APIs.

A player must not be able to request another player's authoritative ticket through a manipulated game/player ID.

Administrative or debugging functionality may have different permissions and should be explicitly protected.

---

# 29. Ticket Lifecycle

The complete ticket lifecycle is:

```text
Game initialization
       ↓
Generate ticket
       ↓
Validate ticket
       ↓
Persist ticket
       ↓
Send ticket to player
       ↓
Numbers are called
       ↓
Player marks valid numbers
       ↓
Ticket state changes
       ↓
Prize evaluators inspect ticket
       ↓
Game finishes
       ↓
Ticket remains available as historical game data
```

---

# 30. Ticket Invariants

The backend must always preserve these invariants:

1. Every active GamePlayer has exactly one ticket.
2. Every ticket contains exactly 15 numbers.
3. Every row contains exactly 5 numbers.
4. Every ticket has 3 rows and 9 columns.
5. Numbers are within the valid 90-ball ranges.
6. A number cannot appear twice on the same ticket.
7. Numbers within a column are ordered correctly.
8. Blank cells contain no number.
9. Players cannot modify their ticket structure.
10. Players cannot generate their authoritative ticket.
11. A ticket is generated before the game enters `IN_PROGRESS`.
12. A player's ticket does not change after reconnection.
13. Only called numbers may be marked.
14. Only numbers belonging to the player's ticket may be marked.
15. Spectators cannot modify ticket marking state.
16. Prize evaluation uses server-authoritative ticket data.
17. Invalid tickets must never become playable tickets.
